# 3B Wallet Security Model — Draft v1

Architecture only. No production keys, seeds, funds, wallet addresses or blockchain activation are created by this document.

## Goal

If 3BC ever leaves the current disabled staging state, wallet security must not depend on React, Unreal, Supabase or one server possessing a user's private key.

## Separation

- Passport identity: application identity.
- Game XP / Coins: server-authoritative application balances.
- Wallet public identity: optional future cryptographic identity.
- Wallet private key: never an application database field.
- Vault reserve keys: separate from user-wallet keys.
- Node keys: separate from Vault and user keys.

Passport user_id may map to a wallet public address, but wallet private material must remain cryptographically independent from the Passport database.

## Preferred user-wallet model

### Phase A — testnet
- local signing only;
- key generated by an audited wallet/signing library;
- private material stored with platform secure storage when available;
- no raw key sent to Supabase;
- no raw key logged;
- signed transaction submitted to the network/API;
- testnet-only assets with zero monetary value.

### Phase B — production candidate
Evaluate two explicit models before implementation:

1. Non-custodial:
   - user/device controls signing;
   - recovery must be designed without a universal server master key;
   - device loss is a first-class recovery scenario.

2. Threshold-assisted recovery:
   - signing/recovery split across independent factors;
   - no single application server can reconstruct the wallet;
   - recovery actions are delayed, audited and user-visible.

A custodial model requires a separate legal/security decision and must not emerge accidentally from storing private keys server-side.

## Device security

Where supported:
- iOS Keychain / Secure Enclave;
- Android Keystore / StrongBox;
- Windows hardware-backed protection where available.

Secure hardware is an isolation layer, not proof that the entire wallet is secure.

## Transaction authorization

A future signed transaction must commit to at least:
- chain/network identifier;
- protocol version;
- sender/public key;
- recipient;
- amount;
- asset identifier;
- fee policy if any;
- account nonce or sequence;
- expiry/validity window where applicable;
- transaction payload hash.

Changing any signed field must invalidate the signature.

## Replay protection

A transaction valid for one network must not be replayable on another.

Minimum:
- unique chain ID;
- account nonce/sequence;
- canonical serialization;
- transaction hash;
- duplicate rejection.

## Backup and recovery

No recovery design is accepted until all cases are tested:
- phone loss;
- reinstall;
- forgotten recovery secret;
- stolen unlocked device;
- compromised recovery factor;
- migration to a new cryptographic suite.

Recovery must never require support staff to receive a user's raw private key or seed.

## Logging

Never log:
- seed phrases;
- private keys;
- decrypted recovery shares;
- bearer tokens;
- signing secrets.

Allowed security telemetry:
- public address;
- transaction hash;
- suite/version;
- anonymized device class;
- failure category;
- timestamp.

## Wallet invariants

- No server API accepts private_key or seed fields.
- No client receives Vault material.
- Wallet balance is derived from the authoritative ledger/chain, not local state.
- A signed transaction executes at most once.
- Account switch clears cached wallet identity before another Passport is loaded.
- Testnet and production key material are never reused.
